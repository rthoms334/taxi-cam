# Bounded native interface inventory

This helper reports camera/renderer string, export and decoded-reference metadata from the mapped **main executable**. Two explicit modes additionally inspect narrowly defined renderer-service and active-aircraft object fields. It does not implement a camera or establish a callable renderer interface. A matching string can be a log message, type name, configuration key, or unused code. Export RVAs can identify code, data, or forwarders; signatures and calling conventions remain unknown.

The discovery code is separate from the installed graphics bridge. It has no startup hook, timer, simulator launch, or deployment step.

## Build and test

Run from the repository root after `bootstrap.ps1` has installed the pinned compiler:

```powershell
.\tests\diagnostics\test.ps1
```

The script builds with the pinned LLVM-MinGW compiler and treats project warnings as errors. It runs synthetic loaded-PE and reference tests, checks the actual LLVM decoder against synthetic instructions, inspects the helper's own image, parses the JSON, and confirms that the explicit-PID mode rejects the PowerShell test host. Outputs stay in the ignored `build/tools/diagnostics/` directory. The tests do not read the simulator. The LLVM library path is generated from the pinned toolchain when building these developer tools.

The standalone executable defaults to inspecting itself:

```powershell
.\build\tools\diagnostics\camera-interface-inventory.exe --self
```

To inspect an already running simulator, supply its verified PID explicitly using `--pid`. The executable accepts no process-name search, process list, wildcard, or automatic target selection. It requires all of these checks to pass:

- The selected process opens with `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`.
- Its executable basename is exactly `FlightSimulator2024.exe`, ignoring case.
- Its token's user SID matches the current user's SID.
- The single module handle requested from the loader has the same full filename as the process executable, or both paths have the same Windows volume/file identity. The latter accommodates Xbox/package path aliases and opens file attributes only.
- Its reported image bounds agree with the parsed AMD64 PE32+ image.

An access or identity failure returns JSON with an error and Windows error code where applicable, and exit code 1. Invalid arguments return exit code 2. The helper does not change privileges or retry with stronger access. There is no process injection, thread creation in another process, memory write, protection change, or function resolution/execution.

## Read boundaries and output

Image reads check the selected image's bounds and call `VirtualQuery` or `VirtualQueryEx`. Only committed `MEM_IMAGE` regions with the exact main-module allocation base and a documented readable protection are accepted. Guard, no-access and execute-only pages are skipped. Readable copy-on-write pages are supported: this installation maps even its PE headers as `PAGE_EXECUTE_WRITECOPY`. The ordinary scans separately reject writable PE sections; narrowly defined exceptions are described below. `ReadProcessMemory` copies only a bounded local chunk and must report every requested byte.

The two explicit object modes, `--camera-service` and `--camera-aircraft`, have separate readers for their fixed object fields. Each object read must fit wholly inside one committed, readable `MEM_PRIVATE` region verified by `VirtualQueryEx`; guard, no-access and execute-only pages are refused. Service mode permits one eight-byte object word. Aircraft mode permits only one-, four-, eight- or sixteen-byte reads within its aggregate budget; the one-byte read is restricted to the selected-object stage's renderer flag. These modes do not expose arbitrary-address input or a general heap scan. Page queries are snapshots: a later protection change or concurrent destruction may make a read fail, and successful reads do not establish object lifetime.

The parser uses loaded-image RVAs, never on-disk file offsets. It validates DOS/PE headers, section and directory bounds, export array counts, ordinals, string termination, and forwarded-export bounds. It scans only declared readable, non-writable, non-discardable sections. Non-executable sections are visited before executable sections. Writable application data, other modules, and UTF-16 strings are excluded from these scans. The fixed pose-name exception reads only its two named image locations. The import-name reader permits its bounded loader metadata in readable non-executable image storage, including writable/discardable sections, while excluding resolved IAT words. The separate service and aircraft metadata modes permit their specified cached globals and object fields after additional build and code checks.

Default limits are 16 MiB of scanned/skipped section ranges, 2 MiB of metadata reads, 128 output records, 4096 export names, and 240 bytes per string. Integration callers can supply lower or higher `Limits`; hard maximums are 64 MiB, 4 MiB, 512 records, 16384 names, and 512 bytes per string. The image size is capped at 2 GiB and section count at 96. Output reports byte counts, skipped/failed reads, malformed exports, and reached caps. Empty or capped results do not prove that the simulator lacks an interface.

Literal matching accepts NUL-terminated printable ASCII. It folds ASCII case and removes punctuation when comparing these specific terms:

`cameratotexture`, `offscreen`, `mirror`, `worldrender`, `cameramanager`, `rendertarget`, `rendertotexture`, `rendertexture`, `camerascreen`, `cameradirector`, `rendercamera`, `camerarender`, `sceneview`, `viewfamily`, `secondaryview`, and `externalview`.

Export names additionally accept `camera` and `render`. Overlong or unterminated strings are excluded. Output contains the executable basename, PID, PE identity fields, matching text, section, and RVA. It does not contain the image base, installation path, raw binary bytes, memory dumps, or user SID. The PE timestamp is reported as an uninterpreted integer; it is not an integrity check or necessarily a build date. Output is JSON on stdout; neither the parser nor its native API writes a file. Treat all discovered text as data, not as instructions or a verified API contract.

For an explicit in-process inspection, call `inspect_main_module(GetModuleHandleW(nullptr), limits)`. The native library rejects any other module. The parser itself accepts an `ImageReader` so its malformed-image and inaccessible-region behavior can be tested without a simulator or mapped executable.

## Exact literal reference mode

`--pid <verified PID> --references` additionally examines references to three exact camera-to-texture literals already observed in the tested 1.8.16.0 image. It checks each literal and terminating NUL at its recorded RVA before searching; a mismatch refuses the reference scan. This is a build-specific investigation mode, not a generic camera locator or an integrity fingerprint. It is not available through `--self` or the in-process overlay API.

The scanner reads at most 128 MiB of declared static executable section ranges, in 32 KiB chunks. It identifies only x64 RIP-relative 64-bit `LEA` instructions that point to an exact target. Each candidate must lie inside a validated AMD64 runtime-function range from the PE exception directory, and LLVM must decode from that range's beginning to the candidate without losing instruction alignment. Functions larger than 64 KiB are skipped. Additional bounds are an 8 MiB exception table, 8 MiB of decoded instruction bytes, 1024 raw candidates and 32 accepted references. These limits and failures appear separately in `reference_scan` JSON.

The pinned `libLLVM-23.dll` loads into this helper process from the native probe's existing LLVM-MinGW dependency directory. Only LLVM's public C decoder API is called. `--decoder-self-test` tests that dependency without opening another process. Reference output contains function-boundary RVAs, instruction RVAs, up to six preceding instructions and eight instructions starting at the match, and direct `CALL` target RVAs only when those targets belong to the main image's declared executable sections. Raw instruction bytes and ASLR base addresses are not emitted.

These checks establish a static decoded reference, not execution, reachability, a constructor, an object instance, a calling convention, or a usable camera API. The scan is deliberately incomplete: other instruction forms, uncovered code ranges and functions without usable runtime-function bounds may contain additional references. This scan does not recover RTTI graphs; the separate aircraft mode now has the narrow numeric RTTI reader described below. No discovery mode invokes private functions. See [the camera entry contract](../../docs/camera-entry-contract.md) for the current evidence and interface constraints.

`--camera-callers` uses the same bounded scan and instruction validation for E8 rel32 calls to six fixed routines: entry creation, setup, visibility, manager update, renderer-record reset and entry-payload destruction. It skips the earlier broad string/export inventory. Call sites must be validated five-byte instructions; targets must be static main-image code. The 128 MiB counter covers newly scanned ranges and excludes chunk overlap, the bounded candidate-function reads, and metadata. It is not an exhaustive call graph, and reaching a cap does not prove the absence of additional callers.

## Bounded camera-registration contexts

`--pid <verified PID> --camera-context` follows eight fixed locations established by previous captures: registration, the registered callback, the engine's manager initialization, and their allocation/creation callees. `--camera-methods` follows five entries observed in the manager's static pointer table plus the earlier camera-to-texture diagnostic function. `--camera-view-setup` follows eight direct callees observed in its setup/update paths. These modes accept no arbitrary addresses. They check the three exact camera-to-texture literals before decoding, retain same-user/main-image identity checks, and read only permitted static sections. MSFS only needs to be open to its main menu; the installed probe is unchanged.

These modes skip broad string and code scans. The generic context reader defaults to a 4096-byte function prefix and permits explicit limits up to 16384 bytes, while retaining a **32768-byte aggregate code cap** and eight-request limit. The fixed CLI modes use 16384 so the already identified 8735-byte initialization function can be inspected completely. A request that crosses the remaining aggregate budget is truncated; exhausted requests receive no code reads. Output records function and instruction RVAs, decoded instruction text, direct-call targets, errors, and truncation. Partial or failed function captures return a nonzero exit status. The image inventory's scan/export truncation flags describe intentionally omitted broad scans here; use `function_contexts.partial` for context completeness.

Completeness refers to the selected PE runtime-function ranges. Optimized methods can span multiple ranges, including fallthrough and branch targets beyond a captured range. A fully decoded range is therefore not proof of complete control-flow coverage. Methods without validated exception-table bounds are refused; two observed table entries were excluded for that reason.

After successful function validation, these modes inspect the static table at RVA 133571232, whose address the captured callback stores at object offset zero. The pointer reader permits at most 32 eight-byte words plus one preceding word (264 bytes); the adapter currently requests 24 (200 bytes maximum). It stops at the first entry not verified as readable static executable storage. Target addresses are normalized to main-image RVAs; external pointer values are discarded. The preceding word is metadata only. A run of code pointers does not establish vtable extent, RTTI identity, method signatures or safe invocation.

They also inspect up to 148 bytes of static PE load-config metadata when that directory is present. The CFG dispatch-slot address is normalized without reading the slot contents. Absence is a valid metadata result, not proof of CFG dispatch: the observed simulator image has the Guard CF header characteristic but no exposed load-config directory.

PE metadata, the runtime-function table (bounded at 8 MiB), exact literals and pointer-table words are additional reads beyond the code cap. The image inventory's metadata-byte counter excludes the runtime-function table and later captures; each component reports its own available counters. No target pointer is called or dereferenced by the pointer reader, no raw code bytes are emitted, and no process memory is modified. The recorded findings distinguish decoded behavior from inferred object contracts.

The view-setup mode additionally reads eight fixed static string RVAs derived from captured instructions. These reads stop at NUL, accept printable ASCII, and use at most 128 bytes including NUL per request, 1024 total. Failed strings remain errors; successful peers are retained. The view-state mode follows a curated set of renderer/entry methods and continuation ranges, with the same code limits; the source profile changes as explicit follow-ups are investigated. Saved JSON records the exact requested ranges for each observation.

View-state mode also inspects two fixed potential pose-type names at RVAs 165937400 and 166129720. This narrow exception permits readable, non-executable, non-discardable writable image data only after the exact AMD64 build tuple is checked. It reads at most 128 bytes including NUL per name, 256 total. The observed printable strings lack the expected MSVC type-name prefix: they remain **unverified diagnostic text**, with errors and a nonzero CLI result even when the code capture is complete. Nonprintable, unreadable and unterminated strings expose no partial text. The ordinary string reader still refuses writable sections.

## Explicit leaf and branch prefixes

`--camera-leaves` captures validated caller contexts, then follows six explicit E8 call sites to small leaf routines. Each call instruction is read again and must still point to its requested static executable target. Prefixes are capped at 64 bytes each and stop at a decoded RET; the generic helper allows eight requests, 512 target bytes and 40 proof bytes. No runtime-function extent is inferred for these leaves.

The same mode then examines three explicit branch edges from those fresh leaf prefixes. Only unprefixed relative JMP/Jcc encodings of 2, 5 or 6 bytes are accepted. Current opcode, target, decoded text and proven instruction boundary must match before a target prefix is read. This adds at most 512 target bytes and 48 proof bytes in the generic helper; the current three requests are smaller. It does not recursively follow branches. Both inventories retain successful peers and report refusals separately. Neither a RET nor a full 64-byte prefix proves logical function completeness, execution or ABI compatibility.

The separate `inspect_slot_prefixes` helper accepts one to eight explicit static vtable-slot/expected-entry RVA pairs. Before target access, it requires an aligned eight-byte slot wholly inside declared readable, non-writable, non-executable, non-discardable main-image data. It rereads exactly that word, normalizes the pointer against the checked loaded-image bounds, and requires an exact match to the requested readable static executable entry. A stale, foreign or mismatched pointer refuses the prefix without reading target code. The caller supplies the preceding fresh object/vtable identity check; a static code pointer alone does not establish that identity.

Each verified slot permits at most 64 target bytes, clipped to its executable section and decoded linearly until an instruction-aligned C3/C2 RET or the read boundary. The aggregate limits are **512 attempted target bytes plus 64 attempted slot-proof bytes**, including failed exact reads. No runtime-function or call-site proof is required, no branch or outgoing call is followed, and no object is read by this helper. Output contains only normalized proof-slot/entry/instruction RVAs, decoded text, counters, and explicit stop/error state. `prefix_limit` or `section_end` without RET remains a valid bounded prefix, not a complete method. A failed request marks the inventory invalid while retaining successful peer metadata.

## Cached renderer service metadata

`--pid <verified PID> --camera-service` validates the known service accessor, viewport output code and individual-entry erase code, then inspects four fixed words:

1. Eight bytes at cached renderer global RVA **173790384**, in declared readable writable main-image data.
2. The cached object's first eight bytes, through a one-shot reader restricted to a committed readable `MEM_PRIVATE` region containing the whole word.
3. Eight bytes at its validated static main-image vtable plus **808**, requiring a target in readable static executable main-image storage.
4. Eight bytes at the same vtable plus **104**, requiring the same target-code properties for the cleanup method.

Before reading these words, the adapter requires the three exact camera literals, complete selected runtime-function captures, and the observed build metadata: **PE timestamp 1787653788, image size 235963904, and 14 sections**. It also matches the decoded cached offset in **4164736** and selected accessor/virtual-slot instructions in **66809728** and **17646000**, including the **+808** and **+104** loads, the cleanup call's RCX/RDX preparation and the exact dispatch instruction at **17646438**. A mismatch reports `build_context` and performs no service-pointer reads. This is an exact check against selected evidence from the observed 1.8.16.0 build, not a cryptographic image identity or validation of every instruction.

This mode adds at most **32 bytes of pointer metadata: 24 image bytes and one 8-byte object word**, including attempted reads that fail, to the usual bounded code/header validation. The whole vtable prefix through both slots must fit declared read-only, non-executable image data; only the two fixed slot words are read. It does not read another object field, invoke the lazy accessor, follow either method target, initialize a service, or modify memory. Results contain only image-relative vtable/slot/method RVAs, including `cleanup_slot_rva` and `cleanup_method_rva`; the cached object address and other absolute addresses are not emitted. A later cleanup-slot/target failure retains earlier verified metadata but leaves `valid=false` with the failing stage and an error. A null cache reports unavailable and the CLI exits nonzero. Concurrent object destruction or a failed validation stops the check; it never retries with a broader read. This is a read-only snapshot, not an ownership guarantee for later execution.

The saved **`build/msfs-1.8.16.0-camera-renderer-create-cleanup-methods.json`** observation resolved vtable **134482536**, slot **134483344** (+808) to method **64652608**, and slot **134482640** (+104) to method **70351808**, using all 32 permitted pointer bytes without a read failure. These are build-specific metadata observations. The separate decoded-method captures and [entry contract](../../docs/camera-entry-contract.md) describe their known behavior and incomplete control-flow coverage; successful pointer resolution alone does not establish camera output or safe cleanup.

## Active-aircraft facade metadata

`--pid <verified PID> --camera-aircraft` inspects the fixed world/user path behind the captured active-aircraft lookup. It is an explicit same-user simulator mode, unavailable through `--self` or the in-process overlay API. It accepts no object address, index or method offset from the command line.

Before object reads, it requires the three exact camera literals and complete bounded contexts for **37638528**, **58093024**, **57963344**, **17648544**, **56053760**, **4164736** and **31727952**, with the existing main-image checks. The seventh context supplies the later key-lookup proof. The selected instruction text must match the cached-world global load, container count/array offsets, user count/array offsets, user facade offset **448** and facade virtual-slot offset **1256**. It also validates the direct-call prefix for **67705600** and its explicit branch to **67705650**, matching the viewport count at **+120**, signed inline-storage selector at **+124**, first ID storage at **+80**, and the zero-count branch's return value **-1**. A mismatch reports `build_context` without reading object fields. The core separately requires the exact AMD64 tuple **timestamp 1787653788, image size 235963904 and 14 sections**, valid section bounds and a non-overflowing loaded-image range before accessing its cached global.

The metadata step follows only these fields:

1. Read the eight-byte cached container pointer at main-image RVA **173790496**, requiring readable, writable, non-executable image data. Read its signed world count at **+20**, bounded to **0..64**, and array pointer at **+24**.
2. Visit at most 64 sixteen-byte world handles. A nonnull control pointer at handle+0 must have DWORD **control+28** equal to DWORD **handle+8**; only then read payload pointer **control+0**. Null or stale references are skipped. Resolve the world's **+40** node handle with the same rules.
3. Require node DWORD **+120** to be nonzero. When signed DWORD **+124 <= 9**, read the first signed viewport ID directly at **node+80**; otherwise read the pointer at **node+80** and only its first signed ID. Negative IDs skip that world. Select the **first** qualifying world and stop enumeration.
4. Read that world's signed user count at **+736**, bounded to **0..64**, and array pointer at **+784**. Resolve **user index zero only** with the same handle-generation checks, then read the user's **+448** facade pointer and the facade's first eight-byte vptr word. An unavailable user does not trigger a search of later worlds.
5. Require the facade vtable prefix through **+1256..1263** to fit declared read-only, non-executable main-image storage. Read only that slot's eight-byte pointer and require its target to be declared readable, read-only executable main-image code. Normalize the vtable, slot and target to RVAs; do not read or invoke the target here.

The core and native adapter cap **attempted object reads at 8192 bytes**. Each base-stage read is exactly 4, 8 or 16 bytes; failed reads count against the budget. The base metadata step reads at most **24 image bytes**: the initial global word, method slot and final global reread. Later stages reuse the same native object reader, so their combined attempts share the adapter's 8192-byte cap rather than receiving a fresh allowance. These limits are additional to the bounded code, headers, runtime-function metadata, literals and static pointer-table validation. No names, text, other users, additional viewport entries or unlisted object fields are read.

Before reporting success, it rereads the selected container count/array, chosen world/node/user handles, their control generations and payload pointers, viewport fields, and facade pointer/vptr. It then rereads the cached global itself. Any changed or unreadable field refuses the result without following a new pointer or retrying the walk. This detects changes observed by the recheck; it is **not an atomic snapshot or lifetime guarantee**, and it does not freeze earlier skipped worlds or establish permission to call the resolved method.

The JSON `aircraft` object reports `valid`, `cached_present`, `selected`, `stage`, `error`, attempted image/object bytes, read failures, world count, worlds examined, selected world index, user count, viewport ID, `facade_vtable_rva`, `method_slot_rva` and `method_rva`. It never emits absolute container, world, node, control, user or facade addresses. Missing data reports an unavailable stage; stale references cannot resolve a facade. Unavailable or failed metadata returns a nonzero CLI status. A method RVA retained before a failed final recheck remains unverified and must not be treated as a successful result.

The loaded-A380 capture **`build/msfs-1.8.16.0-a380-aircraft-facade.json`** completed with **one world, one user, selected world index 0 and viewport ID 0**, using **272 object bytes and 24 image bytes**, with no read failure. It resolved facade vtable RVA **133538936**, slot RVA **133540192** (+1256), and method RVA **56053760**. This identifies the facade method reached by the observed lookup path. It does **not** establish that camera-entry mode-zero keys are `CameraDefinition` GUIDs. That earlier capture contained no key comparison; the later bounded membership stage is described below. No private method is called by either capture.

After that fresh successful result, the adapter uses the static-slot helper to capture `aircraft_method_prefix`. The optional controller stage is enabled only for facade vtable **133538936** and method **56053760**, with the decoded instructions at **56053766** and **56053779** matching the reads at **facade+1648** and virtual-slot offset **432**. It calls the metadata reader again with that fixed facade identity, repeats the complete world/user/facade walk, then reads only the **facade+1648** controller pointer, its first eight-byte vptr, and its static vtable **+432** word. The two new object fields join the consistency recheck; the complete vtable prefix through the slot must fit static read-only data and the method must resolve to static executable image storage. A null object, changed chain, identity mismatch or failed slot validation prevents success.

This optional stage uses at most **32 image bytes** per metadata invocation. `aircraft_controller` reports `object_present`, `object_vtable_rva`, `object_method_slot_rva`, `object_method_rva`, stage/error and separate counters. Its fresh successful slot is checked again by `inspect_slot_prefixes` for `aircraft_controller_method_prefix`; this adds at most **8 proof bytes and 64 target bytes**, separately reported. These reads inspect the resolved method without invoking it or emitting controller addresses.

The third, optional selected-object stage is implemented by the core's `inspect_selected_object` boolean, defaulting to `false`. 2. Read the eight-byte cached renderer pointer at image RVA **173790384**, requiring readable, writable, non-executable image storage, then its single byte at **+2800**. If that byte equals **1**, use index **0** without reading the controller index; otherwise read signed DWORD **controller+672**. Require **0..63** as an inspection cap. 3. Resolve the sixteen-byte handle at **controller+296** using the same generation checks, then read the resolved owner's array pointer at **+752**. Resolve exactly one sixteen-byte handle at `array + index * 16` with the same checks.

No method is called.

All newly read object fields join the consistency recheck, and both cached globals are reread before success. Null/stale handles, a negative validity value or a missing renderer report unavailable; out-of-cap indices, invalid static metadata and failed or changed reads refuse the result. This stage allows at most **56 image bytes** per metadata invocation and shares the same **8192-byte native object budget** with the first two stages. Its synthetic single-world fixtures consume **458 object/56 image bytes** when the renderer byte selects index zero, or **466/56** when the controller index is read. These fixture counts are separate from the saved live observations above.

The `aircraft_selected_object` JSON reports `valid`, `available`, `selected_object_present`, `controller_validity`, `selected_object_index`, the selected object's normalized vtable/slot/method RVAs, stage/error and counters. On fresh success, `aircraft_selected_object_method_prefix` adds a separate static-slot proof and at most 64 target bytes. No object address, name, pose, array contents, GUID or camera key is emitted; resolving this method still does not establish the selected object's full type, lifetime or callable ABI.

The fourth, optional component stage uses the `inspect_component` boolean, also defaulting to `false`. It requires selected-object inspection and the exact selected vtable **133503528** and method **55874752**. Before enabling it, the adapter validates the fresh slot prefix's `lea 368(%rcx), %rax` followed by RET, the direct call to component helper **55914960**, its branch to **80718912**, and the explicit success branch from **80718942** to **80718962**. The latter returns the indexed eight-byte pointer from the component array; it is captured through **80718969**. The gate also checks that the original manager-update caller clears **R12D at 17648675**, then prepares **EDX=5+R12 at 17648861** before its call at **17648869**. The captured intervening instructions do not overwrite R12; its zero value is required to interpret the requested component type as five.

The component stage repeats the earlier validated graph and follows only these additional fields:

1. Resolve the sixteen-byte generation handle at **selected object+368**, yielding the aircraft payload pointer. Read its first eight-byte vptr and require it to normalize into declared read-only, non-executable main-image storage. No aircraft method is read or called here.
2. Read the aircraft's collection pointer at **+19272**, the collection's signed count at **+36**, bounded to **0..64**, and its eight-byte-pointer array at **+40**.
3. Visit component pointers in order. For each nonnull pointer, read only its DWORD type at **+32**. Select the first type **5**, then read only that component's first eight-byte vptr and normalize it under the same static-data requirements. Stop before later candidates.

Every scanned component pointer and type, including candidates before the match, joins the consistency trace. A changed earlier candidate therefore refuses a completed result instead of silently changing which component was first. Each metadata invocation uses at most **56 image bytes** at this stage. Unavailable or stale handles and a missing type-five component remain unavailable; invalid counts, bounds, static vptr locations, read failures or changed fields refuse success. This is still a series of read-only observations, not an atomic snapshot or object-lifetime guarantee.

## Import identity and numeric component RTTI

The aircraft mode now verifies the imported cast helper through `inspect_import_slot`. Fresh proof must show the thunk at **122292224** jumping through IAT slot RVA **213668704**. The reader identifies that one slot using PE import descriptors and `OriginalFirstThunk` name metadata. It never reads the requested resolved-function word or any other word in the declared IAT extent, never substitutes loaded `FirstThunk` pointers for missing name metadata, and never opens the imported DLL. The requested slot is excluded even before directory discovery; header reads must end before the first validated section, preventing malformed header aliases from reaching IAT storage.

The import reader permits at most **256 descriptors**, **2048 lookup thunks per descriptor**, **128 bytes including NUL per module/symbol name**, and **131,072 attempted metadata bytes** overall. Each field/name stays within readable, non-executable main-image data. Writable and discardable section flags are allowed specifically for this loader metadata; native page checks still apply. Missing lookup metadata or an ordinal-only import is explicitly unavailable. Invalid ranges, reserved bits, aliases and failed reads refuse the result. These are separate image-metadata limits, outside the aircraft object-read allowance. Output is import names, normalized metadata RVAs, status and counters, without resolved pointer values or an import-target authenticity claim. The underlying layout is documented in [Microsoft's PE format specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format).

After the component walk succeeds, fresh manager-update instructions must match the observed cast arguments and call. `inspect_rtti_metadata` then reads numeric MSVC AMD64 metadata starting at the component's static vtable: its preceding pointer, a 24-byte signature-one Complete Object Locator, a 16-byte Class Hierarchy Descriptor, up to 64 four-byte base-array entries and their 28-byte Base Class Descriptors. The COL self-RVA, root type and all bounds must agree. Actual reads require readable, non-writable, non-executable, non-discardable main-image sections. TypeDescriptor references may identify writable data, but their headers and names are neither read nor queried. Nested hierarchy references remain numeric; no nested hierarchy, vbtable, object field or code is followed. These layouts follow [LLVM's Microsoft C++ ABI implementation](https://github.com/llvm/llvm-project/blob/main/clang/lib/CodeGen/MicrosoftCXXABI.cpp).

The numeric reader has a separate **4096-byte attempted-read cap**; its present one-level layout needs at most **2096 bytes** for 64 records. Generic source/target presence flags are not cast results. The pure `verified_camera_component_layout` helper additionally matches the exact observed six-record profile: component vtable **133516648**, locator **146401552**, complete-object/target type **165937384**, source type **166129704** at index **2**, zero COL offset and constructor displacement, and the saved hierarchy/descriptor identities. All six PMDs are **(0, -1, 0)**, attributes are **64**, and contained-base counts descend **5..0**. This narrow check supports zero adjustment for the subsequent fixed field reads; it is not a general `dynamic_cast` implementation, an executed cast, or an object-lifetime guarantee. No pointer is accepted, adjusted or returned by the pure helper.

## Fixed camera-key membership

The fifth metadata pass uses `inspect_camera_keys`, defaulting to `false`. It requires component inspection and the exact component vtable **133516648**. It reads only the unsigned DWORD count at component **+108**, capped at **0..64**. A zero count completes without reading the array pointer. Otherwise it reads the pointer at **+112**, exactly the declared number of eight-byte record pointers, and sixteen key bytes at each **record+72**. A null array or record refuses completeness rather than skipping the entry. The two comparison candidates are the configured tail GUID **`F6B3984D-4D58-41C4-8BA8-32CD24CCC13B`** and gear GUID **`89B25433-6454-43DF-9B91-BF338A906A19`**, expressed using the byte ordering of [Guid.ToByteArray](https://learn.microsoft.com/en-us/dotnet/api/system.guid.tobytearray). Every count, array/record pointer and key joins the bounded **512-field consistency trace**, alongside the selected graph and both cached globals. Changed or unreadable fields refuse completion. All five passes reuse one native object reader with an aggregate **8192-byte attempted-read cap**; the fifth pass has at most **56 image bytes** for its fixed globals/slots and rereads. ## Display identity scan

`display_identity_build.ps1` builds `build/tools/diagnostics/display-identity-scan.exe` and tests it against a stand-in process: it must refuse another executable and tie a planted name to its fake texture chain. It never reads the simulator during the build.

The scan looks for the simulator object that ties a cockpit display texture name from `panel.cfg` (`texture=`, for example `DUS` or `$GAUGES_UNIFIED`) to the native D3D12 texture the bridge tracks. Take a **PFD routing** snapshot first: the bridge then writes `%LOCALAPPDATA%\Taxi Cam\snapshots\display-candidates.txt` with every display-shaped texture's ID and native address. Then run, with the simulator's PID:

```powershell
.\build\tools\diagnostics\display-identity-scan.exe <pid> "$env:LOCALAPPDATA\Taxi Cam\snapshots\display-candidates.txt" DUS EICASCDU > identity-report.txt
```

On the tested Store 1.8.16.0 image (PE timestamp 1787653788, SizeOfImage 0xE108600) it first walks the VCockpit panel registry found by static decode of the `panel.cfg` reader: a static array of up to 64 panel pointers at `exe+0xA50B160` with its count at `+0x200`; each 0x690-byte panel holds its `texture=` name inline at `+0x88` and its section name at `+0x528`. For each panel it follows heap pointers up to three levels deep and prints any path that reaches a tracked native texture (`FOUND panel+0x…->+0x… = native #id`). Other builds skip this walk. `--panels-only` stops after it; otherwise the full scan below follows.

It opens only that PID, with `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`, after checking the exact `FlightSimulator2024.exe` basename and the same user. It reads every committed, readable, non-guard region in 16 MiB chunks and reports qwords holding each native address, occurrences of each name (ASCII and UTF-16), one level of references back to both, and name references that lie within 0x800 bytes of a texture reference, with annotated memory around them. Reading the whole address space pages memory in and can take tens of seconds. Matches show where to look; they do not prove an object layout. The report contains process-local addresses, so keep it local.
