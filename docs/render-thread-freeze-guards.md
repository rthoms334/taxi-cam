# Render-thread freeze guards

The bridge runs on the simulator's threads: command-list recording hooks, `Close`, `Reset`, device creation hooks, the `ExecuteCommandLists` wrapper (application render thread, Present and frame-generation helpers, other injectors' helpers) and the D3D12 private-data release that retires our metadata. None of those threads may be parked on a bridge lock. A bridge worker may hold a lock for milliseconds (discovery, private compose submission, pipeline preparation); the same lock taken blocking on a simulator thread turns that into a visible stall, and a lock cycle through a driver-internal lock turns it into the soft freeze reported in issues 27, 53 and 69 (frames and telemetry stop, bridge worker keeps logging).

## Rule

Simulator threads acquire bridge locks through `BoundedLock` (`src/shared/bounded_lock.hpp`) with a budget and skip their work for the current frame when it expires. Budgets: 100 us per-command recording hooks (including the capture manager's `successful_reset`, which every recording thread reaches many times per frame), 500 us Close-time PFD delivery, 1 ms `ExecuteCommandLists` ordering, 5 ms creation and destruction paths. Waiters call `SwitchToThread` every 64 spins so a preempted holder can run. Issue 71 timing without that yield showed about ten times more expired 100 us waits. Individual waits can still exceed their budget by milliseconds when the waiting thread itself is preempted. Bridge-owned threads keep ordinary blocking locks.

The native `Reset` hook holds `observation_mutex` only while it qualifies the observation epoch and resets the list's own recording state. It releases the mutex before the render-boundary identity reset and the capture-manager retirement, which take their own locks, so one thread's Reset does not wait while another thread retires its previous recording. Render-boundary Reset and invalidation first look for an entry under the hook's list pointer with the caller's generation. That match needs no readability probe (`VirtualQuery` and `ReadProcessMemory`) or unwrap. A proxy argument or a fixture key that does not match falls back to the checked `registry_key` path.

A skip always leaves the bridge in a state that refuses injection rather than guessing:

| Path | On an expired wait |
| --- | --- |
| `find_list` registry miss | Null result; the next successful lookup of that list on the same thread invalidates the recording once (state between miss and hit was untracked). |
| `OMSetRenderTargets`, render-pass targets, clears | Targets cleared, `raw_om_known=false`, submission proof `contended`, copy proof invalidated. |
| `SetGraphicsRootSignature` | Observed root cleared; the stamp restore refuses an incomplete state. |
| `stage_pfd`, `drain_pfds`, barrier copy, `copy_patch`, `stamp_at_recording_end` | No PFD write this recording (`skipped_pfd_writes`, `runtime_writes`). |
| Device hooks (resource, RTV/DSV, descriptor copy, root creation) | Entry stays unrecorded; a skipped descriptor copy or RTV marks the view maps stale so no write trusts them until `discover_pfds` clears and relearns them. Missed source candidates are registered by the worker. |
| Capture-manager barrier, target and invalidation-report callbacks | The exact evidence (list, generation, barrier or report) is pushed into the manager's lock-free deferred ring and replayed onto that recording by the next lock holder: every locked evidence callback, `register_consumer_recording`, and every transaction drain the ring first, before the batch is classified or applied. Nothing global is invalidated for a skip. A skipped draw is simply not recorded (no capture from that draw; never infers RT). Skipped capture requests (`record_copy*`, `record_render_target_*`) and source-candidate or list registrations return false and publish nothing: an unregistered list already wipes at submission as an unknown list. |
| `successful_reset`, `destroy_command_list` (lifetime release) | Same ring, in push order with the evidence, so a Reset skipped after evidence on the same list still retires it before later evidence or an Execute. No uncertainty is published. Ring overflow (256 entries) is the one skip that may still wipe: a lost entry may have been a Reset, so every current recording is invalidated until its next observed Reset and the models are wiped once (`deferred_overflows`, wipe origin `deferred_overflow`). |
| `before_submission` ordering fallbacks | Escape exactly like the PR 31 contended path: owned recordings marked before the forward, source uncertainty published after it through `forwarded_unordered`. No transaction, so no unpaired `queue->Wait`. A batch is never treated as unrelated while the deferred ring is non-empty, and an escape with a non-empty ring publishes the queue's source models. The published uncertainty is **not** a wipe: the escaped recordings were never applied, so no model can have left its last positively observed RT state. The next drain retires the device's live models to `other` (retained RT kept, like a named-source PassState report) and rearms them in place on the same lock holder (`retire_sources`, `source_retirements`, `retire_<origin>` counters); only the draw evidence is lost, and the next ordered draw captures again. The bounded consumer escape (`unordered_consumers`) and the legacy contended refusal take the same path. Only ring overflow still wipes. |
| `remember_display_settlement` (Close) | The settlement rows go into a lock-free ring; the next registry lock holder (a later Close, the next `plan_display_submission`, the worker) replays them in Close order before reading `settled_state`, so the PR 68 arm-to-first-stamp carried cover is never refused for a skip. Only ring overflow sets `settlement_stale`; the worker then forgets the settled states without advancing `covered_serial`, so the next observed Close re-arms the cover instead of waiting for a new instrument write. Counters on the `PFD boundary copy:` record: `carried_covers`, `settlement_skips`, `settlement_replays`, `settlement_stale`, `carried_refused_stale`. |
| `Resource::retire` -> handoff | Deferred to the worker; ring overflow raises the handoff's global lifecycle event. |

`finish_transaction` remains blocking on `mutex_`: it runs on the thread that already owns `submission_mutex_` and must `Signal` the timeline it queued a `Wait` on. It holds `mutex_` only for CPU bookkeeping and for recording and closing the private tail lists; the tail `ExecuteCommandLists` and the `Signal` run with `mutex_` released (the packets stay `in_flight`, and only this thread touches the transaction while it owns `submission_mutex_`), so recording threads never expire their evidence budgets behind a driver-bounded queue call.

Every global source-model wipe (`Tracker::invalidate_all`/`clear`) goes through one helper that records its `WipeSite` (`fail_device`, `deferred_sources` with the publisher origins, `unknown_lists_no_owner`, `unknown_lists`, `invalid_recording`, `lease_overflow`, `refused_transaction`, `observer_disabled`, `session_reset`; `unordered_consumer` remains in the enum for old logs) and, for `deferred_sources`, the per-origin count (`wipe_escape_unordered`, `wipe_refused_completed`, `wipe_refused_contended`, `wipe_deferred_overflow`, `wipe_unordered_consumer`; only `deferred_overflow` should ever move). Scoped retirements are counted apart (`source_retirements`, `retirement_restored`, `retire_<origin>`). With `TAXI_CAM_GRAPHICS_DIAGNOSTICS=1` the worker logs one `Source-state wipe:` line per wipe and one `Source-state retire:` line per retirement with the counters that moved since the previous tick, and `Source-state rearm: restored=` when `CaptureProgress` rearms the retained RT models after a genuine wipe.

The parked rate floor (`ParkedRatePolicy`) is not a lock but shares the rule that a skip or jitter must not step the schedule: parking needs 3 s below 0.2 kt, unparking needs a sample at or above 0.35 kt and happens at once, and the 0.2–0.35 kt band holds the current state (a rolling aircraft never accumulates park time). Live 0.9.56 stepped the inset 5<->10 fps at the single 0.2 kt edge while creeping.

## Presentation watchdog

`src/bridge/freeze_watchdog.hpp`, hosted on a dedicated bridge thread that reads atomics only. The pulse counts hooked `ExecuteCommandLists` on registered direct queues plus hooked `Close`. If the pulse stops for 3 s while the bridge is connected, the watchdog closes the graphics gate (`observation_enabled()` false, PFD plans `not_ready`, capture manager escapes every submission) with an atomic store, the worker disarms cameras and observation on its next iteration, and one `Presentation watchdog:` line is logged with the contention counters. After 5 s of frames it re-arms and logs again. SIM_FRAME telemetry stalling while frames continue (pause, menu) is logged once and does not trip; it substitutes for the pulse only before the first submit has been observed.

Closing the gate CPU-signals the bridge timeline value already passed to `ID3D12CommandQueue::Wait`. The watchdog thread does this without taking a bridge mutex, so a ReShade 6.8 immediate-command-list flush blocked on its own fence can finish once the GPU passes that timeline point. `released_waits` counts each CPU signal. The gate also stops new transactions and makes the degraded state visible.

## Log counters

`Render-thread contention:` every 5 s: `armed`, `pulse`, `queue_calls`, `queue_contended` (submit lock busy: other threads on the same queue), `manager_evidence`/`manager_lifecycle`/`manager_submit`, `unordered`, `gated`, `released_waits`, `deferred_retirements`, `deferred_evidence`, `deferred_overflows`, `deferred_lifecycle`, `runtime_writes`, `watchdog_trips`, `last_stall_ms`, `notifications` (enabled/published), `hook_failures`, `failure_rate_peak`, `admission_halted`, `wipes`, `last_wipe`, `unordered_consumers`, `contended_invalidations` (recordings invalidated on the hit after a contended `find_list` miss), `unobserved_admissions` (lists admitted mid-recording), `source_retirements`, `retirement_restored`, `last_retirement`, the per-origin `wipe_<origin>`/`retire_<origin>` pairs, then the bridge sites `registry_recording`, `registry_close`, `registry_creation`, `registry_lifecycle`, `observation_recording`, `handoff_lifecycle`, `skipped_pfd_writes`. High `queue_contended`/`unordered` with low bridge skips means another injector's pressure on the queue, not bridge lock contention.

## Notifications

`src/shared/sim_messages.hpp` maps events to text. The bridge worker and the watchdog thread publish admitted events into a lock-free `SimEventLog` (atomics only, no lock, nothing on a render thread); the worker copies it into `Status::notifications` (IPC protocol 12) and the companion shows unseen fresh events as Windows tray notifications from its UI thread (`Shell_NotifyIcon`, `NIF_INFO`, warning icon for alerts). The companion sets process AppUserModelID `TaxiCam.Companion` (required for `NOTIFYICON_VERSION_4` toasts on Windows 10/11), keeps icon/tip identity on `NIM_MODIFY`, and does **not** set `NIIF_RESPECT_QUIET_TIME` so Focus Assist game-mode cannot silently drop banners while MSFS is fullscreen; the status-line `notice` and a taskbar flash are the fallback when the OS still hides the banner. Setting `settings.ini` `[messages] notifications` (default on; the protocol 10 key `in_simulator` is read and replaced on save) and the tray toggle "Show notifications".

Toast policy (`sim_event_toasts`, applied by the bridge before the limiter and again by the companion on intake): only events the pilot must act on, or would otherwise not notice while MSFS is full-screen, reach the desktop — **simulator unsupported** (cameras stay off), **presentation stalled** (watchdog trip; hooks released), **camera startup failed** (cameras stopped and will not retry) and **hook storm** (disarmed for the simulator process). The other tracked events — connected, cameras ready, connection stopped, cameras disarmed and presentation resumed (the worker's echo of a watchdog or storm disarm, already announced once by the event itself), aircraft mismatch and capture paused — are refused before the limiter, so they neither toast nor consume the budget; they remain in the companion status line, the tray tooltip and `bridge.log`. Toasting events keep the per-event repeat interval and the 4-per-20 s budget, so even a repeating fault does not spam. `tests/app/sim_messages_test.cpp` `toast_policy` holds the per-event table. `SimConnect_Text` is no longer used: it is deprecated in MSFS 2020/2024, the `MESSAGE_WINDOW` type does not exist there and `PRINT_*` only feeds the Assistance tips overlay, so the live check on 0.9.42 rendered nothing.
